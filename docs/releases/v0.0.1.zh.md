# DeepShell Agent v0.0.1 版本收口

> **产品：** DeepShell Agent
>
> **Tagline:** A desktop agent powered by DeepSeek Harness.
>
> **版本：** `v0.0.1`
>
> **阶段：** POC（Proof of Concept，概念验证）
>
> **状态：** Pass
>
> **收口日期：** 2026-09-08

## 1. 收口结论

DeepShell Agent `v0.0.1` POC 已完成收口，结论为 `Pass`。

本版本证明以下核心架构路线可行：

1. 官方 DSH Web UI 可以作为 DeepShell Agent 的最小桌面 UI 载体。
2. Tauri 2/Rust 可以作为桌面壳，负责窗口、生命周期、回环安全边界和 Sidecar 监督。
3. Bundled Node.js + pinned official DSH npm runtime 可以随 macOS arm64 `.app` 分发并启动。
4. DeepShell 可以通过公开 DSH Profile/Bundle/Plugin 机制完成最小 Branding 和 Coding Preset 集成。
5. 官方 DSH 的 Workspace、Session、Streaming、File/Shell Tool、Sandbox 和 Approval 语义可以支撑 POC 纵向闭环。
6. Sidecar 启动握手、Ready Gate、正常退出、有限崩溃恢复和进程树清理在 POC 范围内通过验证。

该结论只表示 `v0.0.1` 已完成可行性验证，不表示 DeepShell Agent 已达到 MVP、生产发布或公开分发标准。

## 3. 范围

### 3.1 已完成范围

- 创建可运行的 macOS arm64 `.app`。
- 直接复用官方 DSH Web UI，不 fork、不 monkey patch DOM、不依赖私有 React 实现。
- 通过公开插件/Bundle/Profile 机制显示 DeepShell Agent 产品名、tagline 和独立品牌标识。
- 使用 `deepshell` Coding Preset，基于官方 `standard` 机械派生并移除 `tool-web`。
- 使用官方 Models Settings 配置 DeepSeek API Key。
- 使用官方 Workspace 创建、Session 创建、文件读写、Shell、Sandbox 和 Approval 流程。
- 使用独立 DSH_HOME，避免污染用户已有 DSH CLI 环境。
- 实现 Tauri 侧 Sidecar 启动、Ready Gate、状态展示、正常退出、崩溃恢复和进程树清理。
- 完成手工 MT、自动化 AT、Gate 和最终 POC 报告收口。

### 3.2 明确不属于本版本

- 不提供完整产品 UI。
- 不实现 Svelte 或自建 Web UI 路线。
- 不实现 Keychain Credential Provider。
- 不开发自定义权限系统或 Safety Guard Plugin。
- 不启用 Web Search、Web Fetch 或 MCP Server。
- 不实现 Tauri File Picker、文件树、文件预览或完整文档能力。
- 不覆盖 Windows、Linux、Intel macOS 或公开分发。
- 不完成 Developer ID 签名、公证、自动更新或安装器。

## 6. 公开仓库边界

本文件是公开版 release closeout（版本收口）说明，只保留可公开的结论、范围和风险接受。原始需求推演、设计草案、实施计划、手工验收记录、自动化证据、Gate 明细、包内容 manifest 和许可证机器清单保留在本地 `docs/plans/` 过程文档目录，默认不随公开源码仓库发布。

公开仓库应保留：

- 架构文档：`docs/architecture.md`
- Roadmap：`docs/roadmap.md`
- release 收口文档：`docs/releases/`
- 源码、构建脚本、锁定清单和测试代码

公开仓库不提交：

- 完整 runtime、构建缓存和安装后的依赖树；
- 本地 `.app`、`.dmg`、installer、E2E staging manifest；
- 未脱敏日志、截图、诊断包、手工验收原始记录或私有证据；
- 真实 API Key、Cookie、启动 token、Prompt、Tool Output 或用户本地路径。

## 7. 已知限制与风险接受

| 限制/风险 | v0.0.1 结论 | 后续处理 |
|---|---|---|
| `credentials-local` 同用户读取风险 | POC 接受并记录。沿用官方凭据文件方案时，同一 OS 用户权限下被诱导的 File/Shell Tool 可能读取本地凭据文件。 | MVP 前评估 Keychain Provider、Secret boundary 和诊断脱敏策略。 |
| 包体积偏大 | POC 接受。主要来自完整 Node.js 与完整 DSH 依赖树。 | 进入 runtime slimming 设计，但不要在未验证前破坏完整官方 DSH 路线。 |
| `AT-028` 专用 soak 脚本缺失 | POC 接受为 manual-assisted evidence，由手工性能观察和包体积读数支撑。 | MVP 前补确定性的 30 分钟 soak 自动脚本。 |
| macOS 公证缺失 | POC 接受。当前仅验证本地包结构，使用 ad-hoc deep signing。 | MVP/发布前准备 Developer ID 签名和 notarization。 |
| 跨平台未覆盖 | POC 不覆盖。 | MVP 或后续版本单独验证 Windows/WebView2、Linux/WebKitGTK 和 Intel macOS。 |
| DSH 上游 Developer Preview 变更 | POC 固定 `0.1.2-rc.1`，不浮动升级。 | 后续升级必须重新跑 profile、bundle、E2E 和安全边界比较。 |

## 8. 交付状态

`v0.0.1` 已作为 POC 收口，不再继续追加 POC 范围内功能。后续新增能力应进入 `v0.1.0` MVP 范围切分，或作为新的 `v0.0.x` 技术验证单独立项。

当前仓库尚未形成 release commit 或 tag；本文件仅记录公开源码仓库可保留的 POC 收口结论。提交、打 tag、归档产物或对外分发需要单独执行发布流程。

## 9. MVP 前建议优先项

1. 明确 `v0.1.0` MVP 范围和不做范围。
2. 增加 30 分钟 soak 自动化，补齐 `AT-028` 的自动证据。
3. 做 runtime slimming 设计与验证，优先评估 Node headers、非目标平台文件、source maps 和类型文件。
4. 改进 `runtime_failed`、`runtime_stop_failed`、重复崩溃和清理失败的用户可读诊断。
5. 设计正式签名、公证、安装和升级路径。
6. 评估官方 `credentials-local` 是否继续保留，或切换到 macOS Keychain Provider。

## 10. 收口判定

`v0.0.1` POC 可以关闭。下一阶段建议从 `v0.1.0` MVP 需求确认开始。
