# DeepShell Agent v0.1.2 DSH Runtime Refresh Closeout

> **Product:** DeepShell Agent
>
> **Tagline:** A desktop agent powered by DeepSeek Harness.
>
> **Version:** `v0.1.2`
>
> **Status:** Source implementation and local macOS arm64 developer-preview package verification complete. Windows installer validation, real-provider API acceptance, Developer ID signing, notarization, and release publication remain separate gates.
>
> **Date:** 2026-09-10

## 1. Summary

`v0.1.2` refreshes DeepShell Agent from the `v0.1.1` release-hardening baseline to the upstream DeepSeek Harness `0.1.5-rc.1` compatibility set.

The release goal is deliberately narrow: adopt the pinned upstream DSH runtime that includes the DeepSeek `deepseek-flash` / `DeepSeek-V41-Flash` catalog improvements, keep the official DSH Web UI and public extension-point architecture intact, preserve existing credential and permission semantics, and add a fail-safe local backup guard for DSH Session data before the runtime refresh materializes the bundled Profile into `DSH_HOME`.

## 2. Implemented scope

| Area | Status | Notes |
|---|---|---|
| Version metadata | Implemented | App package, Tauri config, Rust package, runtime lock, schema, first-party DSH Bundle, and lockfiles now use `0.1.2` / `@deepseek-ai/dsh@0.1.5-rc.1`. |
| Runtime refresh | Implemented | `runtime/manifest/runtime-lock.json`, root `pnpm-lock.yaml`, and `runtime/manifest/dsh-install/package-lock.json` now lock the DSH `0.1.5-rc.1` compatibility set. |

| Session upgrade guard | Implemented | Tauri now creates a bounded local backup of `dsh-home/sessions` before materializing an upgraded Profile, skips duplicate backups for the same upgrade pair, records metadata without absolute paths, and limits retained backup directories. |
| Failure-safe backup behavior | Implemented | Unit tests cover metadata, bounded retention, no workspace copy, idempotent duplicate skipping, and failure preserving source Session data. |
| Public documentation | Implemented | README, Roadmap, third-party notices, and release closeout documents now reflect the `v0.1.2` / DSH `0.1.5-rc.1` source baseline. |

## 3. Explicit non-scope and remaining gates

This closeout does not claim:

- Windows x64 installer acceptance on real Windows hardware or CI;
- Windows WebView2 first-run, shutdown, process-tree cleanup, or uninstall acceptance;
- real DeepSeek API call acceptance for `deepseek-flash` / `DeepSeek-V41-Flash`;
- macOS Developer ID signing;
- Apple notarization;
- Windows code signing;
- formal signed/notarized public binary distribution;
- user-data backup outside `dsh-home/sessions`;
- workspace backup, workspace migration, or workspace cleanup;
- a new credential, permission, model registry, Session runtime, or Web UI fork.

The current macOS package is a locally verified developer-preview package only. Release publication, Git tag creation, and GitHub Release asset upload require separate maintainer authorization.

## 5. Public/private artifact boundary

Committed public materials may include:

- source code;
- lock manifests;
- tests;
- README / Roadmap / release closeout / third-party notice updates;
- public build and verification scripts.

Ignored/local materials remain outside the public source repository by default:

- `docs/plans/`;
- `runtime/staging/`;
- `runtime/node/`;
- `runtime/dsh/`;
- `runtime/profile-template/`;
- local `.app`, `.dmg`, `.exe`, logs, screenshots, diagnostics, and acceptance evidence.

The pre-upgrade Session backup is runtime data under the user application-data directory. It is not a repository artifact and must not be committed.

## 6. Release outcome and recommendation

`v0.1.2` is closed as a source implementation baseline plus locally verified macOS arm64 developer-preview package artifact. It is suitable for maintainer manual testing of the DSH `0.1.5-rc.1` runtime refresh.

Before tagging or publishing:

1. run one manual upgrade test from an existing `v0.1.1` app-data directory and confirm Sessions still open;
2. run a real `deepseek-flash` / `DeepSeek-V41-Flash` provider call when a valid DeepSeek API key and gateway availability are available;
3. keep Windows binary publication pending until Windows x64 hardware or CI validates the actual installer;
4. keep any public binary release marked as developer preview until signing/notarization gates are complete.
