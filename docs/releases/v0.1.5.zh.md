## 1. 版本范围

- **SEA 单文件运行时**（`REL-028`）：每个安装包只携带一个按平台的 `deepshell-runtime.exe`（Enhanced SEA、Zstd、`@yao-pkg/pkg@6.22.0`），取代解压式的 `runtime/node` + `runtime/dsh` 树；终端用户不再安装或落盘 Node.js、npm、pnpm 或 DSH，机器上也无需预装它们；
- **受控运行时 Cache**：native addon 物化在 `%APPDATA%\com.deepshell.agent\runtime-cache\native\win32-x64\<SEA 摘要前 16 位>`；Cache 按记录摘要逐文件校验与修复、在崩溃遗留后重建，并保持 generation 锁；
- **打包门禁**：NSIS 安装器、portable ZIP、三个 schema 6 package manifest、schema 3 package report、按平台 source-input digest，以及带下述两项声明例外的体积门禁；
- **Windows self-spawn 分流**（`W2-F007`/`W2-F008`，见第 8 节）：SEA entry 现在同时分流两条自 spawn 路径——pkg 的 `child_process` 标记（`PKG_EXECPATH`）与 DSH subprocess Job runner / `windows-acl` sandbox runner 使用的 Windows 原生 `CreateProcess`——并让脚本参数稳定位于 `process.argv.slice(2)`。

## 5. 已声明门槛例外（用户已确认并在此披露）

`runtime/manifest/windows-gate-exceptions.json` 中声明了两项例外。声明显式且可审计；验收工具只放行已声明项，schema 3 report 在 `gateExceptions` 数组中记录它们；未声明的超标仍然阻断。

| `warmRss` | +20% / +64 MiB | 296,224 KiB vs 194,864 KiB（+52.0%，+101,360 KiB） | Windows 平台 Node SEA 会把 raw asset archive（约 59.5 MB）作为私有内存常驻；macOS 上同数据为 file-backed 且可回收（macOS 实测约 +8.3%）。这是应用层无法消除的平台实现差异。 |

## 8. 验收后 review 修复（Windows SEA 阶段）

macOS C1 审计修复还会拒绝被中断的审计进程，以及缺少有效平台审计摘要的 JSON。Rust 漏洞先阻断、等待人工判定严重度与运行时影响。combined staging 已能在替换输出前拒绝 incomplete/dry-run/失败审计及阻断性漏洞。W3c 已在 Windows 复验这些 C1 修复，并从 clean source 重建；2026-09-28 macOS clean-source 构建与打包检查也通过。随后 C2 审查又发现两处门禁缺口：staging 未强制 Windows-local 溯源，License/SBOM/Security 证据未绑定 SEA/source 身份。共享输入修复落地后，W3c 和当前 macOS 资产均只能作为历史证据，仍需 Windows 再次重建及 macOS 复验。不宣称已完成最终 combined staging 或发布。

Windows 阶段执行了 review-fix-loop，并在本次交接前关闭了以下 finding（全部在最终资产上复验）：

- `W2-F001`（Blocker）：64 字符 Cache generation 目录在真实 app-data 下超出 `MAX_PATH`，导致 sharp/koffi 无法加载；generation 目录名改为 SEA 摘要前 16 位；
- `W2-F002`（Blocker，已确认例外）：warm RSS 超出门槛；已声明并披露；
- `W2-F003`（Blocker）：v0.1.4 → v0.1.5 升级遗留 legacy `runtime/node` + `runtime/dsh` 树；NSIS `POSTINSTALL` hook 现在精确清理这两个目录；
- `W2-F004`（Blocker）：真机上所有 spawn 子进程的工具失败，因为 Windows Job runner 会重入 SEA，packaging bootstrap 必须消费 `DSH_SUBPROCESS_RUNNER`；entry 加入互斥分流链（self-spawn 脚本、runner selector、探针、CLI）；
- `W2-F005`（Blocker）：`glob`/`grep` 失败，因为 DSH 搜索 helper 需要 `<executable>-rg.exe`，而 native helper 无法来自 VFS；ripgrep sidecar 随 SEA 一起 staging 并校验；
- `W2-F006`（Medium）：宿主模式 package report 未默认读取本机 Windows manifest，首个运行文件数缺失；
- `W2-F007`（Blocker）：`pwsh` 工具报 `error: --profile <name> is required`——`windows-acl` 沙箱会把命令包装成 runner argv，而 DSH 的 Windows Job runner 通过原生 `CreateProcess` 拉起，从不携带 `PKG_EXECPATH`；entry 现在同样识别 `argv[2]` 的快照内绝对脚本；
- `W2-F008`（High）：自 spawn 的快照脚本丢首个参数，因为 argv 归一化同时移除了 entrypoint 占位与脚本路径；现在只移除占位，脚本参数稳定在 `argv[2]`；
- `W3-F001`（Medium，审计一致性）：门槛例外声明曾硬编码确认轮的实测值；该文件属于构建输入，任何重建都会让记录值漂移却仍被读成最终值。现在 rationale 只保留归因，实测权威值指向 schema 3 report 的 `runtimeAcceptance.gates` 与 size gate 的 `windowsNsis.bytes`，并在本文档披露。修复提交 `3e65099`，随后从 clean commit 重建（input digest `58f4d1ae…` → `ae23c46e…`；SEA exe 字节不变：`a0f12d51…`）。

修复由常驻探针覆盖：`self-spawn-shapes` 断言两条自 spawn 路径的参数契约，`subprocess-chain` 覆盖 `cmd`、`powershell`、`pwsh` 与 `sandbox-acl` 链（Job runner → 原生 `CreateProcess` → ACL runner → 受限令牌子进程）。
