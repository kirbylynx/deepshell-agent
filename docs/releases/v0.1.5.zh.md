# DeepShell Agent v0.1.5 单文件运行时版本

> **产品：** DeepShell Agent
>
> **标语：** A desktop agent powered by DeepSeek Harness.
>
> **版本：** `v0.1.5`
>
> **版本性质：** 运行时架构版本：已安装的 Node.js + DSH 依赖树被按平台的 Enhanced SEA（单可执行文件）sidecar 取代，安装不再携带数万个运行时文件，同时 Session、Provider、凭据与官方 DSH Web UI 保持不变。
>
> **状态：** **已准备为未签名 prerelease 候选。** Windows x64 W0–W3 验收已在最终 clean rebuild 产物上通过（installed/portable 矩阵、升级与回退路径、on-device SEA 证据、用户真机工具复测）。随后 W3b 返工从新的 clean commit 重建全部资产，并重跑受影响证据：真实非 dry-run 安全审计、`windows-preflight-pass` route check、安装/卸载回归、全新启动与应用内 boot、on-device、report 与体积门禁。macOS MAC-01 至 MAC-09 已在 macOS 轮次通过。CI run `36319913120`（success，head `6e660f3`）仅作为同 commit 的独立构建门禁记录。Developer ID/公证与 Windows 代码签名**尚未**完成。
>
> **日期：** 2026-09-27

## 1. 版本范围

- **SEA 单文件运行时**（`REL-028`）：每个安装包只携带一个按平台的 `deepshell-runtime.exe`（Enhanced SEA、Zstd、`@yao-pkg/pkg@6.22.0`），取代解压式的 `runtime/node` + `runtime/dsh` 树；终端用户不再安装或落盘 Node.js、npm、pnpm 或 DSH，机器上也无需预装它们；
- **受控运行时 Cache**：native addon 物化在 `%APPDATA%\com.deepshell.agent\runtime-cache\native\win32-x64\<SEA 摘要前 16 位>`；Cache 按记录摘要逐文件校验与修复、在崩溃遗留后重建，并保持 generation 锁；
- **打包门禁**：NSIS 安装器、portable ZIP、三个 schema 6 package manifest、schema 3 package report、按平台 source-input digest，以及带下述两项声明例外的体积门禁；
- **Windows self-spawn 分流**（`W2-F007`/`W2-F008`，见第 8 节）：SEA entry 现在同时分流两条自 spawn 路径——pkg 的 `child_process` 标记（`PKG_EXECPATH`）与 DSH subprocess Job runner / `windows-acl` sandbox runner 使用的 Windows 原生 `CreateProcess`——并让脚本参数稳定位于 `process.argv.slice(2)`。

## 5. 已声明门槛例外（用户已确认并在此披露）

`runtime/manifest/windows-gate-exceptions.json` 中声明了两项例外。声明显式且可审计；验收工具只放行已声明项，schema 3 report 在 `gateExceptions` 数组中记录它们；未声明的超标仍然阻断。

| 例外 | 要求 | 实测 | 归因 |
| --- | --- | ---: | --- |
| `warmRss` | +20% / +64 MiB | 296,224 KiB vs 194,864 KiB（+52.0%，+101,360 KiB） | Windows 平台 Node SEA 会把 raw asset archive（约 59.5 MB）作为私有内存常驻；macOS 上同数据为 file-backed 且可回收（macOS 实测约 +8.3%）。这是应用层无法消除的平台实现差异。 |
| `windowsNsis` | +10% | 86,519,084 B（+52.4%） | 内嵌 Zstd archive 无法再压缩，而 v0.1.4 的 NSIS 对 `node_modules` 文本具有极高 LZMA 压缩率。portable ZIP 仍低于基线（-7.6%）。 |

## 6. 已知限制（如实记录）

- 预览版未签名：全新机器上预计出现 Windows SmartScreen 信誉警告与 macOS Gatekeeper 提示。验收机器上 SmartScreen 未报警（该机可能已放宽），仍需在干净机器上人工确认；
- CI artifact 只是构建门禁，不属于发布资产；
- 本版本未执行：系统关机/注销路径、GUI 卸载提示交互、清理超时注入、数据回退，以及 `REL-025` 的 macOS 范围（隔离记录退休修复仍仅限 Windows）；
- `dsh web --open` 的浏览器接管路径在 SEA 运行时下不可用（它以 `node --input-type=module --eval` 形态自 spawn）；桌面应用固定以 `--no-open` 启动，因此该路径在应用内不可达；
- 父进程被异常强杀时可能遗留孤儿 SEA sidecar；下一次受控启动或卸载时由 ownership registry 与卸载 hook 终止（真机已验证）；
- 本机配置的 npm 镜像（`registry.npmmirror.com`）不提供 audit 端点；因此 `pnpm security:audit` 固定使用官方 `registry.npmjs.org` 查询通告（可用 `DEEPSHELL_AUDIT_REGISTRY` 覆盖）；正式非 dry-run 审计在任何子审计未真实完成时 fail closed（非零退出码）。

## 8. 验收后 review 修复（Windows SEA 阶段）

Windows 阶段执行了 review-fix-loop，并在本次交接前关闭了以下 finding（全部在最终资产上复验）：

- `W2-F001`（Blocker）：64 字符 Cache generation 目录在真实 app-data 下超出 `MAX_PATH`，导致 sharp/koffi 无法加载；generation 目录名改为 SEA 摘要前 16 位；
- `W2-F002`（Blocker，已确认例外）：warm RSS 超出门槛；已声明并披露；
- `W2-F003`（Blocker）：v0.1.4 → v0.1.5 升级遗留 legacy `runtime/node` + `runtime/dsh` 树；NSIS `POSTINSTALL` hook 现在精确清理这两个目录；
- `W2-F004`（Blocker）：真机上所有 spawn 子进程的工具失败，因为 Windows Job runner 会重入 SEA，packaging bootstrap 必须消费 `DSH_SUBPROCESS_RUNNER`；entry 加入互斥分流链（self-spawn 脚本、runner selector、探针、CLI）；
- `W2-F005`（Blocker）：`glob`/`grep` 失败，因为 DSH 搜索 helper 需要 `<executable>-rg.exe`，而 native helper 无法来自 VFS；ripgrep sidecar 随 SEA 一起 staging 并校验；
- `W2-F006`（Medium）：宿主模式 package report 未默认读取本机 Windows manifest，首个运行文件数缺失；
- `W2-F007`（Blocker）：`pwsh` 工具报 `error: --profile <name> is required`——`windows-acl` 沙箱会把命令包装成 runner argv，而 DSH 的 Windows Job runner 通过原生 `CreateProcess` 拉起，从不携带 `PKG_EXECPATH`；entry 现在同样识别 `argv[2]` 的快照内绝对脚本；
- `W2-F008`（High）：自 spawn 的快照脚本丢首个参数，因为 argv 归一化同时移除了 entrypoint 占位与脚本路径；现在只移除占位，脚本参数稳定在 `argv[2]`；
- `W3-F001`（Medium，审计一致性）：门槛例外声明曾硬编码确认轮的实测值；该文件属于构建输入，任何重建都会让记录值漂移却仍被读成最终值。现在 rationale 只保留归因，实测权威值指向 schema 3 report 的 `runtimeAcceptance.gates` 与 size gate 的 `windowsNsis.bytes`，并在本文档披露。修复提交 `3e65099`，随后从 clean commit 重建（input digest `58f4d1ae…` → `ae23c46e…`；SEA exe 字节不变：`a0f12d51…`）。

修复由常驻探针覆盖：`self-spawn-shapes` 断言两条自 spawn 路径的参数契约，`subprocess-chain` 覆盖 `cmd`、`powershell`、`pwsh` 与 `sandbox-acl` 链（Job runner → 原生 `CreateProcess` → ACL runner → 受限令牌子进程）。

### 8.1 W3b 返工（证据完整性与交付卫生）

Windows 交接审计发现：W3 回传包的二进制资产本身无损，但证据文档已被污染。W3b 返工关闭了五项 finding，并从 clean commit `6e660f3` 重建全部资产（input digest `dad2aba2…`；SEA exe 字节不变 `a0f12d51…`），重跑受影响证据链；CI run `36319913120`（success）为同一 commit 的构建门禁：

- `F-1505-WR001`（High，审计完整性）：单元测试调用 `security-audit.mjs --dry-run`，而 dry-run 会照写正式 `runtime/staging/security-audit.json`，导致回传包中的四项审计全部是 dry-run、顶层 status 却写成 `completed`（覆盖了此前的真实结果）。现在脚本支持显式 `--output`；dry-run 不再写正式路径；正式非 dry-run 审计在任一子审计未真实完成（`dry-run`/`tool-missing`/`failed`/`audit-error`/`completed-unparseable`/空输出）时返回非零退出码；只有四项审计真实执行完成时顶层 status 才是 `completed`。回归测试证明 `pnpm check` 不再修改正式审计与 route check 文件；
- `F-1505-WR002`（High，route check 完整性）：`windows-route-check.json` 以 `windows-preflight-incomplete` 状态交付——MSVC 检测只看当前 shell 的 `PATH`，且单元测试覆盖了正式报告。现在检测回退 `vswhere` 与 Visual Studio 标准安装路径；测试用 `--output` 隔离；Windows 正式检查非 `windows-preflight-pass` 时非零退出；
- `F-1505-WR003`（Medium，文档状态冲突）：过程文档与真实状态同步（requirements/design/implementation-plan 状态头；`w0`/`w1`/`w2` 明确标注“阶段快照，已被最终 W3/W3b 状态取代”；W2 验收文档追加最终解决记录）；真正未执行项保持未执行；
- `F-1505-WR004`（Medium，日志卫生）：证据日志含真实 `C:\Users\<name>` 路径、UTF-8 BOM/CRLF 与 GBK 控制台乱码。命令输出改为逐行 UTF-8/GBK 感知解码，真实用户目录替换为 `%USERPROFILE%`，去除 ANSI 序列，全部文本统一 UTF-8（无 BOM）+ LF；含计算机名与本地路径的原始 `.lnk` 备份改为结构化摘要；对最终回传包执行自动扫描，0 finding；
- `F-1505-WR005`（Medium，交付格式）：外层 ZIP 使用 `\` 路径分隔符，导致 macOS `unzip` 告警并非零退出。现在由仅产出 `/` 的写入器生成，并通过解析原始 ZIP central directory 验证（无 `\`、无绝对路径、无穿越、无符号链接、无重复条目名）；`SHA256SUMS.txt` 保持 `/` 相对路径。
