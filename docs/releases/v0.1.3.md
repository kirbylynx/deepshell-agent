# DeepShell Agent v0.1.3 Windows x64 Platform-Acceptance Release

> **Product:** DeepShell Agent
>
> **Tagline:** A desktop agent powered by DeepSeek Harness.
>
> **Version:** `v0.1.3`
>
> **Release nature:** a **Windows x64 platform-acceptance release** — an **acceptance-driven fix iteration**. This version adds no product capability. Its output is "acceptance completed on real Windows x64 hardware, plus fixes for the platform defects that acceptance exposed."
>
> **Status:** The Windows x64 NSIS installer completed end-to-end acceptance on **real Windows 11 hardware**. Acceptance found and fixed 8 Windows platform defects (4 of them real failures that are invisible on macOS). **The macOS side was not re-accepted in this round**, and this machine cannot rebuild macOS artifacts to prove the macOS baseline is intact.
>
> **Date:** 2026-09-13

## 1. Summary

The goal of `v0.1.3` is to move DeepShell Agent from "macOS-only verification conclusions" to "equivalent acceptance evidence on Windows x64".

This version deliberately adds no product capability. All work falls into three categories:

1. **Make the build environment and packaging pipeline actually run on Windows**: `runtime:prepare` / `profile:prepare` / `tauri build --bundles nsis` / package-manifest capture / security-boundary comparison all ran on real Windows x64 hardware for the first time.
2. **Fix platform defects that only real hardware exposes**: 8 in total, 4 of which are failures the user perceives directly (blank app window, browser opened to a dead page, stray console window, incomplete uninstall).
3. **Produce acceptance evidence**: S1–S13 end-to-end scenarios, T7–T12 supplementary items, the WebView2 difference matrix, the Windows Sandbox capability matrix, and the uninstall-behavior conclusion.

## 3. The 8 acceptance-driven Windows platform fixes

All were exposed by real-hardware acceptance; the first 4 are failures the user perceives directly. The full six-field record lives in `docs/plans/v0.1.3-windows-acceptance/change-log.md`.

| # | Symptom (user-visible) | Root cause | Nature of the platform difference |
|---|---|---|---|
| 1 | **App window blank, no content at all** | Tauri `resource_dir()` returns a **verbatim path** `\\?\D:\...`. The Windows API accepts it, but **Node.js module resolution does not** — `realpathSync` truncates the drive letter to `D:` and throws `EISDIR`, so the Sidecar **never executed a single line**. | On macOS `resource_dir()` carries no such prefix; **this failure cannot occur on macOS** |
| 2 | **Browser opened to a `tauri.localhost` page that can never load** | On Windows/Linux the app-asset protocol is `http(s)://tauri.localhost` (macOS uses `tauri://localhost`). The navigation classifier only recognised the `tauri`/`asset` schemes, so it handed the app's own page to the system browser as an external link. | The protocol form **differs per platform** |
| 3 | **A blank console window appears at startup; closing it exits the app** | Three stacked layers: ① the Sidecar (a console program) launched by a GUI parent makes Windows allocate a visible console; ② same for `taskkill`/`powershell.exe`; ③ **the app itself** lacked `windows_subsystem = "windows"`, was linked as a console subsystem binary, and Windows **allocates a console on every launch**. | Windows-specific process/console model |
| 4 | **Uninstall reports files in use and cannot delete them** | After an abnormal exit the Sidecar becomes an **orphan process** that keeps native libraries memory-mapped; the NSIS uninstaller neither detects nor terminates it. | Windows file-locking semantics |
| 5 | First layer of the console-window fix | Sidecar lacked `CREATE_NO_WINDOW` | — |
| 6 | Second layer of the console-window fix | `taskkill` and two `powershell.exe` calls lacked `CREATE_NO_WINDOW` | — |
| 7 | Diagnostic bundle contained absolute paths, **contradicting** its own `pathPolicy` | The troubleshooting `runtime_paths_resolved` event wrote two install roots into the log; the export-side redactor only registered `%APPDATA%`-style prefixes. | Platform-independent, but only exposed by a real export |
| 8 | **App failed on every startup with no self-healing path** | A leftover `ownership.json` (`state:"quarantined"`) **blocked startup permanently** — that state was only ever written, never retired; the "re-verify and clean up next startup" the code comment promised **was never implemented**. | The same defect exists on macOS (`REL-025`), but **this version deliberately fixed only Windows** |

## 5. Explicit non-scope and remaining gates

This closeout does **not** claim:

- **That the macOS baseline is intact** — this machine has no macOS hardware and cannot rebuild macOS artifacts (§2.4 items M2/M3/M4 received **static review only**);
- **That the macOS build is ready to ship** — no runtime verification was performed on macOS in this round;
- That Linux / WebKitGTK works — **not accepted at all**, and must not be inferred from this version's conclusions;
- Windows code signing / notarization;
- Real DeepSeek API long-conversation, large-file, or MCP acceptance;
- **All 6 dimensions of the `REQ-1303` WebView2 difference matrix** — font and CJK rendering, and the file picker / drag-and-drop / clipboard, were **not measured** in this round;
- **All 8 items of the `REQ-1304` Sandbox capability matrix** — read-outside-workspace not triggering Approval, and the Approval **UI-disconnect** and **timeout** branches, were **not verified** in this round;
- **That architecture §8.2 "UI shows the truth" is satisfied** — see §6;
- **The actual deletion list when the uninstall "delete app data" checkbox is selected** — not measured (destructive). Its behavior is documented from the NSIS template's `RmDir /r`, which is a **code-reading conclusion, not a measurement**;
- **That `REL-024` (orphan Sidecar) is fixed** — **not implemented in this version**;
- **That `REL-022` (per-platform runtime trimming) is implemented** — **not implemented in this version**. The current installer bundles **both platforms' Node runtimes**; the `darwin-arm64` half is **4800 files / 187.5 MB of pure waste** inside a Windows install. This is a **quantified known waste**, tracked for a future version to claim;
- **`REL-023` Windows portable (no-install) ZIP** — **not implemented in this version**;
- **That dependencies are vulnerability-free** — this machine's `.npmrc` points at `registry.npmmirror.com`, which **has no audit endpoint**; `pnpm audit` returns `ERR_PNPM_AUDIT_ENDPOINT_NOT_EXISTS`, so **audit data is unobtainable here**. Dependency scanning therefore **must not** be reported as passed. (The security-audit script previously had a false-pass defect where an audit that never ran reported success; it now reports the failure honestly.)
- A second credential, permission, model registry, Session runtime, or Web UI fork.

## 6. Limitations and gaps that must be recorded explicitly

### 6.1 The macOS baseline is not proven (§2.4 key limitation)

Every conclusion in this version comes from **real Windows x64 hardware**. `AGENTS.md` §7 states that a macOS pass is not a Windows pass; the converse holds too: **this machine cannot rebuild macOS artifacts, so it cannot prove the macOS baseline is intact.**

M1–M6 review status:

| Item | Status |
|---|---|
| M1 No new Command / Capability / permission semantics | ✅ Static review |
| M2 macOS-specific parts of `tauri.conf.json` untouched | ✅ Static review (note: this version **did** change its Windows part — NSIS icon PNG → ICO) |
| M3 Platform-specific changes live behind `#[cfg(windows)]` or platform branches | ✅ Static review |
| M4 macOS checks in the three manifest scripts not weakened | ✅ Static review (16/16 + 5/5 evidence) |
| M5 `pnpm check` green | ✅ **Provable on Windows** (exit 0) |
| M6 Contract tests | ✅ **Provable on Windows** (9 passed) |

**Conclusion: M1–M4 may only be labelled "static review passed"; they must not be stated as "the macOS baseline is intact".**

### 6.2 Architecture §8.2 "UI shows the truth" — **judged NOT satisfied** (decisive evidence)

Architecture §8.2 requires: "The UI must show the capabilities actually in effect for the current session; it must not use a uniform 'sandboxed' wording that hides platform differences."

Earlier rounds recorded this as "cannot be judged" for lack of evidence. After the reinstall, this round obtained **citable source-level evidence**:

| Evidence | Result |
|---|---|
| System prompt (7006 chars) filtered for `permission`/`sandbox`/`approval` | **zero paragraphs matched** → the prompt does not describe permission/sandbox capability |
| `request/header` / `request/context` | only `config` / `adapterDefaults` / `tools` → **no permission description in context either** |
| How the model learned its own permissions | from its own reasoning text: *"**the projcache gives authoritative values**"* → it **read the projection file itself** |
| Web UI frontend assets (91 files / 4.46 MB) searched for `approval` / `permissionMode` / `sandboxMode` | **all zero hits**; `permission` only 4 hits (**all from LICENSE text and syntax highlighters**) |
| Frontend i18n / locale resources | **none exist** |

**Judgement:**

- **The UI neither shows nor hides** — it is **entirely silent** on the permission/sandbox dimension;
- Therefore "**The UI must show the capabilities actually in effect for the current session**" is **not satisfied**;
- While "must not use a uniform 'sandboxed' wording that hides platform differences" is **not violated** — because no such wording exists.

**These two points must be recorded separately**, or "failed to meet a disclosure obligation" gets conflated with "contains misleading wording".

**Relationship to the Windows-specific risk (which aggravates the conclusion)**: on Windows `set_private_directory_permissions()` is a **complete no-op** and measured ACLs are **inherited and not hardened**. With the UI not showing capability at all, the user has **no way to learn** this platform difference — exactly the situation architecture §8.2 exists to prevent. It is not "misled by wrong wording" but "**given no information**"; the practical consequence for the user is similar.

**Disposition**: this version **did not modify** the official DSH Web UI (compliant); the only permissible conclusion is "**record the gap**", not "fix it".

### 6.3 The known S11 uninstall defect (`REL-024`)

Controlled reproduction (start the app normally → kill only the app process, leaving the Sidecar) → a real silent uninstall. Result:

| Item | Result |
|---|---|
| Registry uninstall entry | ✅ Deleted |
| Start-menu / desktop shortcuts | ✅ Removed |
| App data | ✅ Retained (matches "retained by default") |
| **Install directory** | ❌ **5 files / 108.54 MB left behind** |

The 5 residual files: `runtime\node\win32-x64\node.exe` (93.4 MB), `@img\sharp-win32-x64`'s `libvips-42.dll` (18.6 MB) / `libvips-cpp-8.18.6.dll` / `sharp-win32-x64-0.35.4.node`, and `@koromix\koffi-win32-x64`'s `koffi.node` — **each one exactly a library that orphan process had loaded**.

**Causality verification**: after terminating the orphan Sidecar, **those same 5 files immediately became deletable, 5/5**, and the directory tree was then removed. → The direct cause of the uninstall failure is the orphan Sidecar — **not a correlation but a complete causal chain**.

**This defect is not fixed in this version** and is tracked in the Roadmap as `REL-024`.

### 6.4 Other honestly recorded gaps

| Gap | Nature |
|---|---|
| S8 Host-validation strength | A forged `Host` returns **401 (missing credentials) rather than 403 (Host rejected)**, so it is **not provable** that Host validation alone blocks direct access. What actually blocks cross-site **reads** is that responses carry **no CORS headers at all**. Browsers cannot forge `Host`, so this is not an exploitable defect; recorded as a **hardening gap**. |
| One limitation of the S9 verdict | That round **could not capture a pre-close baseline snapshot**, so the verdict rests on the stronger condition "no process matching the Sidecar signature exists after close". It **cannot answer** whether exactly one Sidecar existed before close. |
| T7 methodological deviation | While constructing the "in-flight Tool Call", the model **added `run_in_background: true` on its own**, so what actually got interrupted was the subsequent `job_output`, not the `pwsh` call. The conclusion is unaffected, but the record must match the facts. |
| The macOS twin of `REL-025` | The "quarantined record blocks startup permanently" defect **also exists in the macOS code**; **this version deliberately did not change macOS** (no hardware = unverified change). |
| Dependency vulnerability audit | **Audit data is unobtainable on this machine** (the mirror has no audit endpoint). See §5. |

## 9. Closing

The value of `v0.1.3` is not new capability but that it **proved Windows x64 is a genuinely viable delivery path** and exposed 8 platform defects that only real hardware could find — 4 of which would leave the user unable to use the product at all (blank window, stray browser, console window, incomplete uninstall).

It must also be stated honestly that this version did **not** bring the Windows side to parity with macOS. The WebView2 matrix has 2 unmeasured dimensions, the Sandbox matrix has 3 unverified items, architecture §8.2's "UI shows the truth" cannot be judged, uninstall carries a known defect, dependency vulnerability audit is unobtainable on this machine, and **the macOS baseline is not proven**.

These gaps are tracked item by item in the acceptance record and the Roadmap, and **must not** be treated as resolved because this version "passed acceptance".
