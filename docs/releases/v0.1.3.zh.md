# DeepShell Agent v0.1.3 Windows x64 平台验收版本 收口

> **产品：** DeepShell Agent
>
> **Tagline:** A desktop agent powered by DeepSeek Harness.
>
> **版本：** `v0.1.3`
>
> **版本性质：** **Windows x64 平台验收版本（platform-acceptance release）**，性质为**验收驱动的修复迭代**——本版本没有新增产品能力，产出是"在真实 Windows x64 真机上完成验收，并修复验收过程中暴露的平台缺陷"。
>
> **状态：** Windows x64 NSIS 安装包已在**真实 Windows 11 真机**上完成端到端验收；验收过程中发现并修复 8 处 Windows 平台缺陷（其中 4 处为 macOS 上不可见的真实故障）。**已通过收口审查**（代码零缺陷；文档修复 5 类同步缺陷，见 §9）。**macOS 侧本轮未重新验收**，且本机无法重建 macOS 产物来实证 macOS 基线未破坏。
>
> **日期：** 2026-09-14

## 1. 摘要

`v0.1.3` 的目标是把 DeepShell Agent 从"只有 macOS 侧验证结论"推进到"Windows x64 侧具备**同级验收证据**"。

本版本刻意不新增产品能力，全部工作分三类：

1. **构建环境与打包链路在 Windows 上真实打通**：`runtime:prepare` / `profile:prepare` / `tauri build --bundles nsis` / 产物清单捕获 / 安全边界比较，全部在 Windows x64 真机上首次跑通。
2. **修复只有真机才会暴露的平台缺陷**：共 8 处，其中 4 处是**用户在真机上直接可感知的故障**（应用空白无内容、浏览器被误打开、命令行窗口、卸载删不干净）。
3. **产出验收证据**：S1–S13 端到端场景、T7–T12 补充验收、WebView2 差异矩阵、Windows Sandbox 能力矩阵、卸载行为结论。

## 3. 验收驱动修复的 8 处 Windows 平台缺陷

全部为**真机实测暴露**，其中前 4 项是用户在真机上直接可感知的故障。详细六字段记录见 `docs/plans/v0.1.3-windows-acceptance/change-log.md`。

| # | 现象（用户可感知） | 根因 | 平台差异性质 |
|---|---|---|---|
| 1 | **应用窗口空白、无任何内容** | Tauri `resource_dir()` 返回**逐字路径** `\\?\D:\...`；Windows API 接受，但 **Node.js 模块解析不接受**——`realpathSync` 把盘符截成 `D:` 抛 `EISDIR`，Sidecar **一行代码都没跑起来** | macOS 上 `resource_dir()` 不含该前缀，**此故障在 macOS 上不可能出现** |
| 2 | **浏览器被打开一个必然打不开的 `tauri.localhost` 页面** | Windows/Linux 的 app-asset 协议是 `http(s)://tauri.localhost`（macOS 才是 `tauri://localhost`）；导航分类器只识别 `tauri`/`asset` scheme，于是把自家页面当外链交给了系统浏览器 | 协议形态**按平台不同** |
| 3 | **启动时多出一个空白命令行窗口，关闭它应用一起退出** | 三层叠加：① Sidecar（控制台程序）由 GUI 父进程启动时系统新建可见控制台；② `taskkill`/`powershell.exe` 同样如此；③ **应用自身**缺少 `windows_subsystem = "windows"`，按控制台子系统链接，Windows **每次启动都分配控制台** | Windows 独有的进程/控制台模型 |
| 4 | **卸载时提示文件被占用，删不干净** | 应用异常退出后 Sidecar 成为**孤儿进程**，继续内存映射原生库；NSIS 卸载程序不检测、不终止它 | Windows 文件锁语义 |
| 5 | 命令行窗口修复的第一层 | Sidecar 缺少 `CREATE_NO_WINDOW` | — |
| 6 | 命令行窗口修复的第二层 | `taskkill` 与两处 `powershell.exe` 缺少 `CREATE_NO_WINDOW` | — |
| 7 | 诊断包出现绝对路径，与 `pathPolicy` 声明**自相矛盾** | 排障用的 `runtime_paths_resolved` 事件把两个安装根写入日志；导出侧脱敏器只登记了 `%APPDATA%` 一类前缀 | 平台无关，但只在真机导出时暴露 |
| 8 | **应用每次启动都直接失败，无法自愈** | 残留的 `ownership.json`（`state:"quarantined"`）**永久阻断启动**——该状态只被写入、从未被回收；代码注释宣称的"下次启动核验清理"**从未实现** | 缺陷在 macOS 同样存在（`REL-025`），但**本版本刻意只修 Windows** |

## 6. 必须显式记录的限制与缺口

### 6.1 macOS 基线未被实证（§2.4 关键限制）

本版本的全部结论来自 **Windows x64 真机**。`AGENTS.md` §7 明确规定"macOS 通过不等于 Windows 通过"，其逆命题同样成立：**本机无法重建 macOS 产物，因此无法实证 macOS 基线未被破坏**。

M1–M6 的核对状态：

| 项 | 状态 |
|---|---|
| M1 未新增 Command / Capability / 权限语义 | ✅ 静态复核 |
| M2 未触碰 `tauri.conf.json` 的 macOS 专用部分 | ✅ 静态复核（但本版本**确实改动了** `tauri.conf.json` 的 Windows 部分：NSIS 图标 PNG→ICO） |
| M3 平台差异改动位于 `#[cfg(windows)]` 或平台分支内 | ✅ 静态复核 |
| M4 三个产物清单脚本的 macOS 检查项未被削弱 | ✅ 静态复核（16/16 + 5/5 举证） |
| M5 `pnpm check` 全绿 | ✅ **可在 Windows 上实证**（exit 0） |
| M6 contract tests | ✅ **可在 Windows 上实证**（9 项通过） |

**结论：M1–M4 只能标注"静态复核通过"，不得表述为"macOS 基线未破坏"。**

### 6.2 架构 §8.2「UI 如实展示」—— **判定为未达成**（决定性证据）

架构 §8.2 要求「**UI 必须展示当前会话实际生效的能力**，不得用统一的"已沙箱化"文案掩盖平台差异」。

前几轮因缺少证据而记为"无法判定"。重装后本轮取得了**可引用的源码级证据**：

| 证据 | 结果 |
|---|---|
| 应用系统提示词（7006 字符）按 `permission`/`sandbox`/`approval` 过滤 | **零段落命中** → 不向模型描述权限/沙箱能力 |
| `request/header` / `request/context` | 仅含 `config` / `adapterDefaults` / `tools` → **上下文里也没有权限说明** |
| 模型如何得知自己的权限 | 读其推理原文：*"**the projcache gives authoritative values**"* → 它是**主动去读投影文件**才知道的 |
| Web UI 前端产物（91 文件 / 4.46 MB）搜 `approval` / `permissionMode` / `sandboxMode` | **全部零命中**；`permission` 仅 4 处（**全部来自 LICENSE 与语法高亮器**） |
| 前端 i18n / locale 资源 | **不存在** |

**判定**：

- **UI 既不展示、也不掩盖**——它在权限/沙箱维度上**完全沉默**；
- 因此「**UI 必须展示当前会话实际生效的能力**」**未满足**；
- 而"不得用统一的'已沙箱化'文案掩盖平台差异"**未被违反**——因为根本没有这样的文案。

**这两点必须分开记录**，否则会把"没有兑现展示义务"与"存在误导性文案"混为一谈。

**与 Windows 特有风险的关系（加重结论）**：Windows 上 `set_private_directory_permissions()` 是**完全 no-op**、目录 ACL 为**继承且未加固**。在 UI 不展示能力的前提下，用户**无从得知**这一平台差异——这正是架构 §8.2 要防的情形。虽非"被错误文案误导"，而是"**无任何信息**"，但对用户的实际后果相似。

**处置**：本版本**未修改官方 DSH Web UI**（合规）；结论只能是"**记录缺口**"，不是"修复它"。

### 6.3 S11 卸载的已知缺陷（`REL-024`）

受控复现（正常启动应用 → 只强杀应用进程、保留 Sidecar）→ 真实执行静默卸载，结果：

| 项 | 结果 |
|---|---|
| 注册表卸载项 | ✅ 已删除 |
| 开始菜单 / 桌面快捷方式 | ✅ 已清理 |
| 应用数据 | ✅ 保留（符合"默认不删除"） |
| **安装目录** | ❌ **残留 5 文件 / 108.54 MB** |

残留的 5 个文件：`runtime\node\win32-x64\node.exe`（93.4 MB）、`@img\sharp-win32-x64` 的 `libvips-42.dll`（18.6 MB）/ `libvips-cpp-8.18.6.dll` / `sharp-win32-x64-0.35.4.node`、`@koromix\koffi-win32-x64` 的 `koffi.node`——**每一个都恰好是那个孤儿进程加载过的库**。

**因果验证**：终止孤儿 Sidecar 后，**同样这 5 个文件立即 5/5 全部可删**，目录树随之清空。→ 卸载失败的直接原因就是孤儿 Sidecar，**不是相关性而是完整因果链**。

**该缺陷本版本不修复**，已在 Roadmap 登记 `REL-024`。

### 6.4 其他如实记录的缺口

| 缺口 | 性质 |
|---|---|
| S8 的 Host 校验强度 | 伪造 `Host` 返回 **401（凭据缺失）而非 403（Host 被拒）**，**无法证明** Host 校验单独阻断了直连。真正阻断跨站**读取**的是响应中**不存在任何 CORS 头**。浏览器无法伪造 `Host`，故不是可利用缺陷，记为**加固缺口** |
| S9 判定的一次局限 | 该轮**未取到关闭前的基线快照**，判定依赖"关闭后不存在任何符合特征的侧车进程"这一更强条件。**无法回答**"关闭前是否恰好只有 1 个侧车" |
| S10 的 T7 方法学偏差 | 构造"执行中 Tool Call"时，模型**自行追加了 `run_in_background: true`**，真正被打断的是随后的 `job_output` 而非那条 `pwsh`。结论不受影响，但记录须与事实一致 |
| `REL-025` 的 macOS 同源缺陷 | 隔离记录永久阻断启动的缺陷**在 macOS 代码中同样存在**，**本版本刻意未改 macOS**（无真机 = 未验证改动） |
| 依赖漏洞审计 | 本机**无法获得审计数据**（镜像无 audit 端点），见 §5 |

## 10. 结语

`v0.1.3` 的价值不在新增能力，而在**证明了 Windows x64 是一条真实可用的交付路径**，并暴露出 **8 处只有真机才能发现的平台缺陷**——其中 4 处会让用户直接无法使用产品（窗口空白、浏览器被误打开、命令行窗口、卸载残留）。这批缺陷在 macOS 上**不可能出现**，此前也**从未在真机上跑过**。

同时必须诚实说明：本版本**没有**把 Windows 侧做到与 macOS 侧同等完备。收口时点仍存在的缺口：

- **架构 §8.2「UI 如实展示」已判定为未达成**（UI 完全不展示会话的权限/沙箱能力），而非"无法判定"；
- **架构 §9.3 被违反**（打包了两平台的 Node，Windows 侧 187.5 MB 无用）；
- **WebView2 矩阵有 2 个维度未测**（Markdown 渲染侧、拖放），**Sandbox 矩阵有 2 处未验证**，**T8 六故障域中 2 个存在检测盲区**；
- **卸载存在已知缺陷**（`REL-024`），**新增 3 个缺陷本版本不修**（`REL-025` 的 macOS 侧、`REL-026`、`REL-027`）；
- **依赖漏洞审计在本机不可获得** → **未通过漏洞扫描**；
- **macOS 基线未被实证**（无真机，M1–M4 仅静态复核）。

这些缺口已逐条登记在验收记录与 Roadmap 中，**不得**因本版本"验收通过"而被默认为已解决。
