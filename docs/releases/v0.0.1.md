# DeepShell Agent v0.0.1 Release Closeout

> **Product:** DeepShell Agent
>
> **Tagline:** A desktop agent powered by DeepSeek Harness.
>
> **Version:** `v0.0.1`
>
> **Phase:** POC (Proof of Concept)
>
> **Status:** Pass
>
> **Closeout date:** 2026-09-08

## 1. Closeout conclusion

DeepShell Agent `v0.0.1` POC is closed with a `Pass` result.

This version proves that the core architecture path is feasible:

1. The official DSH Web UI can serve as the minimal desktop UI surface for DeepShell Agent.
2. Tauri 2/Rust can act as the desktop shell for windows, lifecycle, loopback security boundaries, and Sidecar supervision.
3. Bundled Node.js plus pinned official DSH npm runtime can be distributed inside a macOS arm64 `.app` and started successfully.
4. DeepShell can use public DSH Profile/Bundle/Plugin mechanisms for minimal branding and Coding Preset integration.
5. Official DSH Workspace, Session, Streaming, File/Shell Tool, Sandbox, and Approval semantics can support a vertical POC loop.
6. Sidecar startup handshake, Ready Gate, normal shutdown, limited crash recovery, and process-tree cleanup pass within the POC scope.

This conclusion only means that `v0.0.1` completed feasibility validation. It does not mean that DeepShell Agent has reached MVP, production release, or public binary distribution quality.

## 3. Scope

### 3.1 Completed scope

- Created a runnable macOS arm64 `.app`.
- Reused the official DSH Web UI directly, with no fork, DOM monkey patch, or private React dependency.
- Displayed DeepShell Agent product name, tagline, and independent brand identity through public plugin/Bundle/Profile mechanisms.
- Used the `deepshell` Coding Preset, mechanically derived from the official `standard` preset with `tool-web` removed.
- Used official Models Settings to configure the DeepSeek API key.
- Used official Workspace creation, Session creation, file read/write, Shell, Sandbox, and Approval flows.
- Used an independent `DSH_HOME` so the user's existing DSH CLI environment is not polluted.
- Implemented Tauri-side Sidecar startup, Ready Gate, status display, normal shutdown, crash recovery, and process-tree cleanup.
- Closed the manual MT, automated AT, Gate, and final POC report tracks.

### 3.2 Explicitly out of scope

- No complete product UI.
- No Svelte or custom Web UI route.
- No Keychain Credential Provider.
- No custom permission system or Safety Guard Plugin.
- No Web Search, Web Fetch, or MCP Server.
- No Tauri File Picker, file tree, file preview, or complete document capability.
- No Windows, Linux, Intel macOS, or public distribution coverage.
- No Developer ID signing, notarization, auto update, or installer.

## 6. Public repository boundary

This file is the public release-closeout note. It keeps only public conclusions, scope, and accepted risks. Raw requirement exploration, design drafts, implementation plans, manual acceptance records, automated evidence, Gate details, package manifests, and machine-readable license inventories stay in local `docs/plans/` process documents and are not published by default.

The public repository should keep:

- Architecture document: `docs/architecture.md`
- Roadmap: `docs/roadmap.md`
- Release closeout documents: `docs/releases/`
- Source code, build scripts, lock manifests, and test code

The public repository must not commit:

- Full runtime, build cache, or installed dependency trees;
- Local `.app`, `.dmg`, installer, or E2E staging manifest;
- Unredacted logs, screenshots, diagnostic bundles, raw manual acceptance records, or private evidence;
- Real API keys, cookies, startup tokens, prompts, tool outputs, or user-local paths.

## 7. Known limitations and accepted risks

| Limitation/risk | v0.0.1 conclusion | Follow-up |
|---|---|---|
| Same-user read risk in `credentials-local` | Accepted and recorded for POC. With the official credential-file scheme, a File/Shell Tool running under the same OS user could be induced to read local credential files. | Evaluate Keychain Provider, Secret boundary, and diagnostic redaction before MVP. |
| Large package size | Accepted for POC. The main contributors are full Node.js and the full DSH dependency tree. | Design runtime slimming, but do not break the complete official DSH path before validation. |
| Dedicated `AT-028` soak script missing | Accepted as manual-assisted evidence, supported by manual performance observation and package-size readings. | Add deterministic 30-minute soak automation before MVP. |
| macOS notarization missing | Accepted for POC. Current validation only covers local package structure with ad-hoc deep signing. | Prepare Developer ID signing and notarization before MVP/release. |
| Cross-platform coverage missing | Not covered by POC. | Validate Windows/WebView2, Linux/WebKitGTK, and Intel macOS separately in MVP or later versions. |
| DSH upstream Developer Preview changes | POC pins `0.1.2-rc.1` and does not float upgrades. | Every upgrade must rerun profile, bundle, E2E, and security-boundary regressions. |

## 8. Delivery status

`v0.0.1` is closed as the POC. No more functionality should be added to the POC scope. New capabilities should enter the `v0.1.0` MVP scope split or a separate `v0.0.x` technical validation.

The repository does not yet have a release commit or tag. This file only records POC closeout conclusions that can remain in the public source repository. Commits, tags, archived artifacts, or external distribution require a separate release workflow.

## 9. Recommended priorities before MVP

1. Define the `v0.1.0` MVP scope and explicit non-scope.
2. Add 30-minute soak automation to complete deterministic evidence for `AT-028`.
3. Design and validate runtime slimming, prioritizing Node headers, non-target platform files, source maps, and type files.
4. Improve user-readable diagnostics for `runtime_failed`, `runtime_stop_failed`, repeated crashes, and cleanup failures.
5. Design formal signing, notarization, installation, and upgrade paths.
6. Evaluate whether to keep the official `credentials-local` scheme or move to a macOS Keychain Provider.

## 10. Closeout decision

`v0.0.1` POC can be closed. The next stage should start from `v0.1.0` MVP requirement confirmation.
